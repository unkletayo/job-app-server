# 07 — Discovery scheduler + adapter harness

**What to build:** The scheduled-discovery machinery that every real Source Adapter (tickets 08–10) will plug into: periodic scheduling via a Redis-backed queue (BullMQ, per [[0002-tech-stack]]), incremental-fetch checkpointing, per-source rate-limit/backoff, run-outcome recording, and partial-failure isolation. Proven in this ticket using a fake adapter implementing `JobSourceAdapter` — no real external network calls yet. This is Seam 2 (fake adapters standing in for real ones) coming into existence.

**Blocked by:** 05 — discovery of multiple postings needs Job Cluster dedup already in place to be meaningful.

**Status:** done

- [x] A source registered with the scheduler runs on a periodic schedule (default every 6 hours, configurable)
- [x] Each source tracks `last_successful_run`, `last_cursor`/pagination checkpoint, `last_seen_job` — a second run against a fake adapter does not reprocess postings already seen
- [x] Rate limiting (throttling + exponential backoff + jitter) is applied per source
- [x] Each run produces a recorded outcome: jobs fetched, jobs merged into existing clusters, new clusters created, scoring/extraction failures — queryable after the fact
- [x] A failure in one source's adapter (simulated via the fake adapter) does not stop other sources' discovery in the same cycle, and does not crash the worker
- [x] Seam 2 tests: a fake `JobSourceAdapter` is registered, discovery runs, normalized/deduped Job Postings land in Postgres (verified via Seam 1 queries), a second run proves incremental fetching, and a fake-adapter failure proves isolation

## Comments

New `src/job-discovery/` module, wired into `AppModule`. Key design choice: the scheduled-discovery contract is a **new, separate interface** (`DiscoverableSourceAdapter` in `discoverable-source-adapter.ts` — `fetchPage(userId, checkpoint) → {postings, nextCheckpoint, hasMore}`), not an extension of `JobSourceAdapter` (job-postings/source-adapter.ts). `ManualPasteAdapter`/`GenericFetchAdapter` are never scheduled per the spec, so forcing them to implement a discovery method would be pure ceremony; only Sanctioned Source adapters (ticket 08+) will implement this one. Real adapters register into it via the `DISCOVERY_ADAPTERS` DI token (empty `{}` by default in production until 08+ lands).

**Schema**: `DiscoverySource` (per-user-per-sourceKey config + checkpoint: `lastCursor`, `lastSeenJobId`, `lastSuccessfulRunAt`, `intervalMinutes`, `requestsPerMinute`, `enabled`) and `DiscoveryRun` (per-run outcome: status, timestamps, `jobsFetched`/`jobsMerged`/`jobsCreated`/`failureCount`, `errorMessage`). Re-added the `merged` flag to `JobNormalizationService.ingest()`'s `IngestResult` — ticket 05 had dropped it as unused; this ticket is its first real consumer (run-outcome counts).

**Execution split** (mirrors the `JobPostingsService`/`JobNormalizationService` split): `DiscoveryRunnerService.run()` pages one source to completion via the adapter, ingests every posting through the same `JobNormalizationService` pipeline manual-paste uses, and **never throws** — an adapter failure, a missing adapter, or a per-posting ingest failure all land as a recorded `failed`/`succeeded` `DiscoveryRun`, returned not raised. `DiscoveryCycleService.runAll()` loops every registered source calling `run()`, which is what makes one source's failure structurally unable to block another (criterion 5) — isolation falls out of `run()`'s never-throw contract rather than needing extra try/catch gymnastics in the loop (kept one anyway, as cheap defense-in-depth against a future regression in `run()` itself).

**Throttling vs. backoff** are deliberately two different mechanisms: `DiscoveryRateLimiterService` is an in-process per-sourceKey min-interval gate (steady-state pacing, honors each source's configurable `requestsPerMinute`) applied before every `fetchPage` call; exponential-backoff-with-jitter is BullMQ's native job option (`{type:'exponential', delay, jitter}`) on the periodic queue job, applied only when a run actually fails and needs a retry. `DiscoveryProcessor` (the BullMQ `@Processor`) is the one place that turns a recorded failed run into a thrown error, since `run()` itself never throws — that's what makes BullMQ's retry/backoff actually engage.

**HTTP surface** (`DiscoveryController`, Seam 1): `GET /discovery/sources`, `PATCH /discovery/sources/:sourceKey` (config — `enabled`/`intervalMinutes`/`requestsPerMinute`, re-upserting the BullMQ schedule on change), `POST /discovery/sources/:sourceKey/run` (manual trigger, synchronous, same `DiscoveryRunnerService.run()` the queue uses), `GET /discovery/runs`, `POST /discovery/run` (run every registered source in one cycle). e2e tests drive triggering and assertions entirely through this HTTP surface (Seam 1) with a `FakeSourceAdapter`/`FailingSourceAdapter` test double injected via `overrideProvider(DISCOVERY_ADAPTERS)` (Seam 2) — matches the spec's "assertions land through Seam 1 where possible."

**Deviation from ADR 0002's phrasing** ("API (NestJS), worker (BullMQ processor)" as separate concerns): `DiscoveryProcessor` lives in the same module that's imported by `AppModule`, so both the `api` and `worker` Docker services run a BullMQ Worker for the `discovery` queue today. The existing repo has no mechanism to give `api`/`worker` different module graphs (`worker.ts` already bootstraps the full `AppModule`, same as `main.ts`, predating this ticket) — building that split was out of scope here and is flagged for whoever tackles it, rather than done silently. Functionally harmless: BullMQ supports N workers across M processes sharing one queue.

**Dependency snags fixed along the way**: `@nestjs/bullmq@12` is ESM-only and can't be `require()`'d by Jest's CJS runtime — pinned to `11.0.5` (last CJS release, same public API). `bullmq`'s `ioredis` dependency is an *optional peer* it won't resolve under pnpm's strict linking unless the consuming project also depends on it directly — must stay a direct dependency (briefly removed it as apparently-unused, which caused the Worker to loop failing-and-retrying its own connection setup fast enough to OOM the process within seconds; restored it). `msgpackr-extract`'s native build script needed `pnpm approve-builds` (recorded in `pnpm-workspace.yaml`). Jest e2e config now sets `forceExit: true` — standard for BullMQ test suites since a Worker's Redis connections don't always look closed to Jest's handle detection even when `app.close()` ran cleanly. Test Redis is isolated to logical DB 1 (`test/setup-test-env.ts`) so discovery e2e runs never share BullMQ/queue state with local dev.

Full e2e suite (33/33, 7 files) and `tsc --noEmit` pass; `eslint` remains unconfigured in this repo (noted in ticket 06 too). Verified live end-to-end against the running Docker `api` container: unregistered-source run correctly records a `failed` outcome without crashing, `POST /discovery/run` cycles cleanly with zero registered adapters (expected until ticket 08+), and `PATCH /discovery/sources/:sourceKey` persists config changes.

**Not exercised**: the BullMQ periodic scheduler actually firing on its 6-hour timer (tests trigger runs directly via HTTP/service calls, per Seam 2's "fake adapters stand in" — waiting out a real 6-hour interval in a test isn't practical); becomes meaningfully testable once a real adapter's interval is short enough to matter, or via a dedicated fast-interval smoke test if that's ever needed.
